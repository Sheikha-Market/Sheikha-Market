# دراسة حزمة شيخة الموحّدة

SHEIKHA Global Runtime Platform | SHEIKHA UGIT-RP

تاريخ المراجعة: 18 أكتوبر 2026، بتوقيت الرياض.
الحالة: توصية معمارية وخطة تأهيل، وليست شهادة تشغيل أو إذن نشر.

## الخلاصة

الأنسب للمشروع هو **منتج موحّد بوحدات اختيارية، ومثبت خاص بكل نظام ومعمارية، وإضافة خفيفة للمحرر**. نوحّد تجربة الاستخدام والعقود والتحديثات، دون جمع كل الصلاحيات داخل عملية واحدة أو تحميل كل الوحدات عند البدء.

الإضافة والتوسعة تسميتان تعتمد دلالتهما على البرنامج المضيف؛ أما المثبت فهو وسيلة توزيع، وليس بديلاً عن منطق التطبيق. لذلك الاختيار ليس «Extension أو Plugin أو Installer» على نحو حصري.

هذا استنتاج هندسي مبني على الموجود في المستودع. لا توجد في هذه المراجعة قياسات تثبت أن الحزمة الموحّدة أقل استهلاكاً للذاكرة أو أسرع من البدائل.

## المقارنة

| الخيار | موضعه المناسب في شيخة | الحد أو الكلفة |
| --- | --- | --- |
| إضافة VS Code | سياق المشروع، التحرير، الأوامر، مساحة العمل | تعتمد على المضيف، ولا تعوّض تطبيق المستخدم أو خدمة التشغيل |
| Extension Pack | تسهيل تثبيت مجموعة إضافات مستقلة يحتاجها المطور | لا يدمجها في محرك واحد، ولا يثبت سلامتها أو يقلل استهلاكها تلقائياً |
| Plugin متخصص | وظيفة اختيارية بعقد وإصدار وصلاحيات واضحة | يحتاج ضبط توافق وعزل وإيقاف مستقل؛ التحميل الديناميكي ليس هدفاً بحد ذاته |
| تطبيق مكتبي بوحدات | مدخل موحّد للمستخدم وإدارة الوحدات والإعدادات | يحتاج بناءً وتحديثاً واختباراً مناسباً لكل منصة |
| CLI وواجهة ويب | التشغيل الآلي أو الوصول من المتصفح عند الحاجة | لا يعني توفرهما أن خدمة الخلفية أو التكاملات الخارجية جاهزة |
| مثبت لكل منصة | تسليم التطبيق واعتمادياته وترقيته وإزالته | لا يوجد ملف تنفيذي واحد صالح لكل الأنظمة والمعماريات |

في VS Code، يجمع `extensionPack` إضافات قابلة للإدارة بصورة مستقلة؛ الاعتماد الوظيفي يعبّر عنه `extensionDependencies`. [مرجع Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest).

يوفّر Tauri حزم توزيع خاصة بالمنصة ومتطلبات توقيع بحسب وجهة التوزيع. وهذا يدعم توحيد المصدر وتجربة المنتج، لا افتراض مثبت ثنائي عالمي. [مرجع توزيع Tauri](https://v2.tauri.app/distribute/).

قائمة منتجات V2 تصف مرحلتها التاريخية؛ وجود شفرة Tauri لاحقة لا يغيّر تلك اللقطة ولا يرقّي الأهداف القديمة تلقائياً. كذلك لا تعني أرقام إصدارات الإضافة والمخططات والحزمة أنها سلسلة إصدار واحدة.

المرفق الأخير ينتهي عند V36.5. مصدر المحرك المحلي `sheikha_v36_5_universal_app_pack_engine.py` يكتب كتالوجاً من أربع وحدات وحالات ثابتة إلى SQLite وJSON ويحدّث البصمات؛ لا يبني مثبتات ولا يختبر تركيبها. لم أشغّله مجدداً. بصمة المرفق: `fff7dc76a4d767887c5c1b89b09f5686e7b2d6fd7413c881e1dcf26b12b64943`.

## المعمارية المقترحة

1. **واجهة شيخة:** الاستفادة من واجهة سطح المكتب الحالية، مع بقاء الويب خيار وصول، وعدم إنشاء واجهة موازية لمجرد تغيير الاسم.
2. **خدمة تشغيل مشتركة:** عقود محددة للطلبات والنتائج والتحقق من هوية العميل والخدمة. لا تنسخ الإضافة محرك التشغيل أو مفاتيح الحسابات.
3. **وحدات اختيارية:** التطوير، السوق، البيانات، والمحاكاة تفعّل بحسب الحاجة. تظل الأعمال الطويلة والتكاملات الخارجية معزولة عن واجهة المستخدم.
4. **محولات المضيف:** الإضافة الحالية للمحرر وCLI وMCP تستخدم العقود نفسها حيث يناسبها ذلك. لا تُنشأ إضافة متصفح بلا مسار استخدام محدد.
5. **توزيع خاص بالمنصة:** إعادة استخدام مصفوفة V2 ومحوّلاتها، مع حزمة إصدار تربط إصدارات المكونات المتوافقة. لا نصنع مصفوفة منافسة ولا نطمس سجل الإصدارات السابقة.
6. **فصل Bare-Metal:** يبقى منتج إقلاع مستقل الاختبار والتوزيع؛ تثبيت تطبيق شيخة على نظام مضيف لا يُعد تثبيتاً لنواة Bare-Metal.

التطبيق الرئيسي واحد من منظور المستخدم، لكن الإضافة وخدمة الخلفية والوحدات قد تكون مكونات تثبيت مستقلة. لا يحتاج كل مستخدم كل المكونات، ولا تعني الواجهة الموحدة صلاحيات موحّدة للجميع.

## ضوابط التشغيل

- المحافظة على ثقة مساحة العمل وعدم منحها تلقائياً؛ الوظائف الحساسة تبقى محجوبة في الوضع المقيّد. [دليل Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust).
- تسجيل MCP لا يساوي نجاح الاتصال أو التفويض. يُختبر كل مزود بأداة قراءة محدودة، ثم تضبط صلاحيات الأفعال على جهة التنفيذ. مصادقة النقل ليست تفويضاً شاملاً بكل العمليات. [مواصفة تفويض MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).
- لا تنزيل أو تفعيل شامل لإضافات الطرف الثالث، ولا تخزين أسرار في الحزمة أو التقارير، ولا تعطيل فحوص التوقيع لتجاوز عائق التثبيت.
- تثبيت المستخدم المحلي لا يتحول تلقائياً إلى خدمة نظام دائمة أو نشر إنتاجي. تغييرات الخدمة والصلاحيات والحسابات تُراجع بنطاقها المحدد.
- فصل حالات «معلن»، «مبني»، «مثبت»، «اجتاز اختباراً محدداً»، و«معتمد للإصدار». لا نستخدم ACTIVE بديلاً عن نتيجة اختبار موثقة.
- SHA-256 بصمة محتوى، وليس تشفيراً للمصدر أو توقيع ناشر أو إثبات ملكية. لا نستنتج اعتماداً قانونياً أو شرعياً من اسم حقل في JSON.
- احترام مرجعية المشروع بالكتاب والسنة، والخصوصية والأمانة ومنع الضرر، مع مراجعة بشرية مختصة للضوابط التي تتطلب حكماً شرعياً؛ الاختبارات البرمجية لا تصدر هذا الحكم.

## ترتيب التأهيل

| المرحلة | العمل المطلوب | شرط الانتقال |
| --- | --- | --- |
| تثبيت المرجع | تعيين مصدر إصدار الإضافة المقصود ومقارنة الحزمة المثبتة به؛ حفظ الأعمال غير المراجعة | وصفة بناء قابلة لإعادة التنفيذ وإصدارات مكونات متوافقة |
| Linux أولاً | بناء مرشح محدود، واختبار الواجهة وهوية الخلفية والتثبيت والترقية والإزالة في بيئة معزولة | سجلات اختبار مرتبطة ببصمة المرشح، مع خطة تراجع لا تفقد بيانات المستخدم |
| التكاملات | اختبار مزود واحد في كل مرة، ورفض الطلبات غير المصرح بها وفشل الشبكة | نتيجة قراءة فعلية وحدود صلاحيات واضحة، دون تسجيل الرموز السرية |
| Windows وmacOS | تنفيذ البناء والاختبارات الخاصة بكل منصة واستكمال متطلبات التوقيع | أدلة أصلية لكل هدف؛ نجاح Linux لا ينسحب عليهما |
| الإصدار | ربط الحزم بالمصدر وقائمة الاعتماديات SBOM وبيانات المنشأ وخطة التراجع | مراجعة واعتماد إصدار محدد، لا إذن عام دائم |

قبل نسبة تحسين الأداء إلى هذا الاختيار، تُقاس ذاكرة العمليات وزمن بدء التشغيل وCPU في الخمول وحجم الحزمة وزمن الطلبات تحت حمل ثابت، مع تشغيل الوحدات الاختيارية وتعطيلها. لا تُسجل وفورات رقمية قبل القياس.

## حدود هذه الجولة

اكتملت دراسة الاختيار وربطها بالمكونات الموجودة وتوضيح توثيق V2. لم تُبنَ حزمة جديدة، ولم يُجرَ تثبيت أو اتصال سحابي جديد أو تغيير في قاعدة البيانات أو إعادة ختم للأدلة أو نشر. التفعيل على «كل نظام» ليس نتيجة متحققة؛ يلزم لكل هدف بيئة متاحة وأدلة قبول تخصه.

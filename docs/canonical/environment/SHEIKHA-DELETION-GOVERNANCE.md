# حوكمة سلامة الملفات ومنع الحذف

## المبدأ

تُدار سلامة الملفات على قاعدة «لا ضرر ولا ضرار»: لا يُمرر حذف لملف متتبع دون مراجعة بشرية واعية، وفهم أثره، وتوفر وسيلة استرجاع. هذا ضابط تشغيلي للمشروع، وليس فتوى أو ادعاء امتثال شرعي آلي.

## السبب المثبت في فحص 2026-11-02

- أظهر Git عدد 2,373 حذفًا متتبعًا في مساحة العمل، وكانت الحذوفات غير staged وقت الفحص.
- لا يوجد سجل commit يثبت هذه الحذوفات؛ إنها تغييرات محلية غير ملتزمة.
- لم يكن Git hook يسجل أو يمنع أمر حذف نظام الملفات. كما أن فحص ما قبل الالتزام كان يمرر الحالة staged فقط إلى طبقة الحوكمة، فلا يرصد الحذف الموجود في عمود working tree.
- لا تكشف بيانات Git وحدها البرنامج أو الأمر أو الشخص الذي حذف الملفات. تحديد ذلك يتطلب سجلات تدقيق نظام ملفات كانت مفعلة قبل الحذف؛ لا يجوز استنتاج الفاعل من الملفات المفقودة وحدها.

## الضابط المحلي

يفحص `.githooks/pre-commit` الفرق بين HEAD ومساحة العمل، ويوقف أي commit ما دام هناك حذف لملف متتبع، سواء كان staged أو غير staged. يعرض أول 50 مسارًا فقط، ولا يستعيد ملفات تلقائيًا ولا يحذف بيانات.

لحل الحذف، تُراجع المسارات أولًا. لا تُستعد إلا الملفات التي يوافق عليها مالك التغيير صراحة، ثم يعاد تشغيل الفحص والاختبارات ذات الصلة. لا تستخدم `git clean` أو `git reset --hard` أو أوامر استعادة شاملة كإجراء إصلاح.

## الحدود

- هذا hook يمنع commit محليًا، ولا يمنع `rm` أو أداة أخرى من حذف ملف قبل commit.
- يمكن تجاوزه عمدًا بـ `git -c core.hooksPath=/dev/null commit` أو `--no-verify`؛ لذلك هو حاجز وقائي محلي، وليس حدًا أمنيًا ضد مستخدم متعمد.
- لم تُراجع حماية الخادم البعيد أو إعدادات branch protection. الحماية الأقوى تتطلب سياسة على الخادم ونسخًا احتياطية مجدولة مع اختبار الاستعادة.
- عُثر على حذوفات متعددة في working tree؛ لم تُستعد الحذوفات غير الموافق عليها ولم تُغيّر محتوياتها.

## ما ينفذه المحوّل الجديد

الواجهة هي `convert_snapshot(source_bytes, *, target_schema_bytes, expected_source_sha256)`. لا تقبل مسار مصدر أو مسار هدف، ولا تحتوي default يشير إلى الأصل. تثبت بصمة المصدر الممررة وبصمة [SQLالمرجعي](inputs/target-schema-reference.sql)؛ الأخير نسخة مطابقة بايتيًا لمدخلR3، لم تُغيّر.

يقرأ المحوّل جدول `entities_bylaws_articles_catalog` وحده من نسخة خاصة للبايتات الممررة، ويفحص المخطط والأنواع والمفاتيح والتصادمات قبل إنشاء الهدف. الهدف `:memory:` فقط. **لم يُشغّل المحوّل على صفوف الأصل الثلاثة**؛ تجربته الحالية اصطناعية.

| حقول المصدر | التعامل في المرشح |
|---|---|
|الأعمدة العشرة جميعًا|حفظ القيم كاملة في `catalog_claims.payload_json` مع تثبيت مصدر اللقطة|
|اسم الكيان ونوعه|سجل ادعاء بهوية `USER_DECLARED_UNVERIFIED`|
|رقمCR/GOV والختم القديم|يبقيان فيpayload؛ لا يُنشأ منهما معرّف رسمي أو إثبات ملكية|
|رمز المادة ونصها|وثيقة حاوية ونسخة رصد ومادة بدور `SOURCE_CLAIM`|
|التأصيل والحكم المنقولان|حفظ الادعاء كما ورد، مع مراجعتين `PENDING`|
|timestamp|حفظه كما ورد، دون تحويله إلى تاريخ قبول أو نفاذ|

تُشتق المعرفات من بصمة اللقطة والمفتاح الأصلي ونوع السجل. حتميتها تخص **اللقطة نفسها**؛ تغير اللقطة ينتج معرفات أخرى، ولا يثبت هوية كيان دائمة أو يصل تاريخًا عبر اللقطات. `OBSERVED_SNAPSHOT` تسمية رصد، لا نسخة تاريخية مستعادة. تبقى تواريخ الاعتماد والنفاذNULL، ولا تُصدر موافقة شرعية أو قانونية.

تبقى الجداول الـ93الأخرى خارج التحويل؛ **هذا ليس محوّلًا للقاعدة كاملة**. كذلك لا يوجد إخراج قاعدة إلى القرص أو تحويل خدمة حية أو اختبار رجوع لهذا المحوّل. تجربةR3 القديمة لا تسد هذه الفجوات تلقائيًا.

# تكامل Sheikha Firmware وUEFI وSecure Boot V1

## الهدف

توحد هذه الطبقة أدلة إصدار نظام شيخة مع هوية اللوحة وإصدار Firmware وبنية UEFI وحالة Secure Boot. وهي تنتج مرشح توافق قابلًا للمراجعة، ولا تكتب Firmware ولا تغير PK أو KEK أو db أو dbx ولا تنشر إصدارًا تجاريًا تلقائيًا.

المدخلات الحالية إقرارات للفحص البنيوي. لا يتحقق المخطط من توقيع الملفات أو الجهاز بنفسه. اكتمالها يعطي `DECLARED_CHECKS_COMPLETE_PENDING_EVIDENCE_VERIFICATION`، مع `compatibilityProven=false`؛ ولا يجوز وصفه بأنه توافق مثبت. يجب تقديم كل قيمة منطقية صراحة، بما فيها `setupMode` و`bootArtifactRevoked`، ولا يفسر غيابها على أنه أمان.

## سلسلة التوافق

```text
إصدار شيخة + SHA-256 + SBOM + مصدر البناء
                 ↓
هوية اللوحة + إصدار Firmware + توقيعه + نسخة الاسترداد
                 ↓
UEFI + GPT/ESP + تسليم ExitBootServices
                 ↓
Secure Boot: User Mode + PK/KEK/db/dbx + فحص عدم الإبطال
                 ↓
QEMU → جهاز فعلي → وسيط استرداد → TPM/Measured Boot
                 ↓
مرشح توافق → تفويض بشري مستقل → بوابة الإصدار
```

## قواعد الإصدار

- كل لوحة وإصدار Firmware وتركيبة مفاتيح لها سجل مستقل؛ نجاح جهاز لا يثبت جميع الأجهزة.
- يربط سجل `dbx` لقطة القائمة ببصمة SHA-256. التحقق الفعلي من عدم إبطال محمل الإقلاع يتطلب تحليل القائمة والتوقيع، وليس مقارنة بصمة الملف وحدها.
- توليد مرشحات الإصدارات يمكن أتمتته، أما Flash وتغيير مفاتيح Secure Boot وتحديث dbx والنشر الإنتاجي فلا تتم تلقائيًا.
- يلزم وسيط استرداد مجرب فعليًا، وربط الهدف والأثر والتفويض أحادي الاستخدام قبل أي كتابة.
- لا تعني بصمة JSON توقيعًا، ولا تعني نتيجة QEMU تحققًا على العتاد.

## التشغيل الآمن

```bash
npm run -s ops:governance:firmware-uefi-secure-boot:test:v1
```

الاختبار محلي ولا ينفذ `fwupdmgr update` أو `SetVariable` أو كتابة قرص أو TPM. تحديث UEFI dbx الظاهر في واجهة النظام تحديث لقائمة التواقيع الممنوعة؛ يجب فحص توافق كل محمل إقلاع ووسيط استرداد قبل تطبيقه ضمن عقد منفصل.

## الجاهزية

الطبقة البرمجية واختبار حدودها جاهزان. الجاهزية التجارية لـFirmware تبقى مرتبطة بأدلة حقيقية لكل لوحة: التوقيع، Secure Boot، فحص dbx، الإقلاع الفعلي، TPM/measured boot، والاسترداد، ثم موافقة الإصدار المستقلة.

## تحقق الملفات المحفوظة

أضيف أمر CLI محلي إلى أدوات الفوندري:

```text
node tools/training/sheikha-foundry-workbench-v1.js platform-evidence --input PRIVATE_MANIFEST.json
```

يحتوي المدخل `releaseRef` و`boardRef` و`architecture` ومصفوفة `artifacts`. كل عنصر يتضمن `id` و`kind` و`relativePath` و`sha256`. المسارات نسبية لجذر المستودع، والجذور المسموحة ثابتة في أداة CLI: `bare-metal/images` و`runtime/bare-metal` و`reports/private`. لا يحدد المدخل جذور الصلاحية ولا يمنح تصريحا بالكتابة.

القراءة لملفات عادية فقط، بحد 16 ملفا و128MiB لكل ملف، عبر مقاطع لا تتجاوز 1MiB. ترفض الروابط الرمزية ومسارات الأجهزة والخروج عن الجذور، ويرصد تغير الملف أثناء القراءة. لا تشغل الملفات أو محتوى سجلاتها، ولا تقرأ TPM أو متغيرات UEFI، ولا تنفذ QEMU.

تعيد النتيجة لكل ملف `MATCH` أو سبب الرفض. `providedFilesVerified` يعني تطابق الملفات المقدمة فقط. اكتمال الملفات الأساسية Firmware وEFI وdbx يعطي `BYTES_VERIFIED_PENDING_TRUST_CHECKS`؛ لا يتحقق هذا الأمر من التوقيعات أو دلالات dbx أو صحة ادعاء الإقلاع. البصمات المتوقعة وهوية اللوحة واردة من مدخل غير موثق، وليست جذور ثقة. لذلك تبقى `productionReleased=false` و`executionAuthorized=false` حتى مع تطابق الجميع.

لا توجد واجهة HTTP لهذا الأمر. واجهة `/foundry/platform-release/preview` تبقى معاينة إقرارات محمية للمشرف، وترفض حقول مسارات الملفات. تحفظ النتائج التشغيلية الخاصة خارج `public` و`runtime`، بصلاحيات المجلد 700 والملف 600.

رمز خروج `platform-evidence` هو 2 إذا نقص ملف أساسي أو فشلت مقارنة أي ملف، و1 للمدخل غير الصالح، و0 عند اكتمال مقارنة الملفات المطلوبة. الرمز 0 ليس تصريح إصدار أو تحقق توقيع؛ يجب قراءة `remainingTrustChecks` وعدم استخدام بوابة البايتات وحدها للنشر. معاينات التخطيط الأخرى تحتفظ بسلوكها السابق.
